# RQ1 — does VCF Core preserve and represent everything defined in the VCF specification?

Two independent assessments answer that question, both copied here from
[`ecrum19/vcf-core-vocabulary`](https://github.com/ecrum19/vcf-core-vocabulary)
at tag **`v2.1.2`**.

```sh
sh RQ1/run.sh
```

Needs `git` and `python3` with `rdflib`. It clones the vocabulary from GitHub at
the pinned tag — no local copy of that repository is required — and writes to
`results/`.

## The two assessments

**`methodology/`** reads information requirements out of the VCF 4.1–4.5
specification text and tests each against fixtures. **94 requirements over 210
cases.** Every expected answer was authored from the specification before the
query ran, and every passing query is re-run against an emptied graph as a
negative probe, so a query that would pass on anything is caught. Coverage is
reported per version, and an untested requirement scores zero rather than being
excluded. All 94 carry a recorded human review decision.

**`vcf45-inventory/`** is a curated enumeration of the VCF 4.5 logical model:
**104 constructs**, each recorded against three axes — information preservation,
explicit structure, and enforcement. All 104 have preserved structured
representations and 87 additionally have an enforcement rule. Being curated by
the vocabulary's own maintainers, it maps what its authors listed; it cannot
reveal an omission nobody listed.

The two are not comparable and their denominators must never be combined: one
counts requirements read out of a specification, the other constructs on an
authored list.

## What is here

| | |
| --- | --- |
| `methodology/inputs/` | The requirements, the cases, and the recorded review decisions. |
| `methodology/queries/` | The SPARQL each case runs. |
| `methodology/fixtures/` | The VCF files the cases run against. |
| `methodology/sources/` | The pinned VCF 4.1–4.5 specification texts, with `sources.lock.json` giving each one's SHA-256. |
| `methodology/scripts/` | `assess.py` and the source-audit helpers. |
| `methodology/generated/` | `summary.json` — the headline numbers. The bulk outputs are regenerated by `run.sh`. |
| `methodology/REVIEW-REPORT.md` | What the human review checked and what it accepted as a limitation. |
| `vcf45-inventory/` | The construct inventory, its two scripts and their recorded output. |

## Why `run.sh` executes the clone, not the copies here

`assess.py` fingerprints its inputs by path **relative to the vocabulary
repository root**, and the recorded review acceptances are keyed to those
fingerprints. Running the copies in this directory from a different root would
report every requirement as unreviewed — an artefact of where the files sit
rather than a finding about the evidence. So the clone is what executes and this
directory is what you read.

To keep that honest, `run.sh` compares all 138 duplicated files against the tag
before running anything and refuses to continue if any has drifted. The copies
are therefore either identical to the release or the run fails loudly.

The scripts also need `ontology/`, `mappings/`, `examples/` and `scripts/` from
the vocabulary repository, which is a second reason they cannot run standalone
from this directory.

## Not copied

`generated/witnesses/` (6.8 MB of materialized RDF), `results.json`,
`source-audit.json` and `declarations.json` are left upstream. They are outputs,
`run.sh` regenerates them into `work/`, and a stale copy in this repository would
drift from the source without anyone noticing.

Because the copied files are byte-identical to the release, some relative links
inside `methodology/README.md`, `REVIEW-REPORT.md` and `vcf45-inventory/README.md`
point at upstream paths that do not exist here. Repairing them would fail the drift
check, so they are left as the release wrote them.
