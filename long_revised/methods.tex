\section{Methods}
\label{sec:methods}

\subsection{Representation and assessment design}
\label{sec:design}
\label{sec:profiles}

VCF Core was developed iteratively from the earlier VCF-RDFizer vocabulary~\cite{crum2025semantifying}, using AI-assisted drafting and expert human review to derive terms, field definitions, and constraints from VCF 4.1--4.5~\cite{htsspecs,vcf45}.
It represents files, header declarations, records, and sample observations as distinct resources, linking each field value to the declaration needed to interpret it (Figure~\ref{fig:model}).
A \term{VariantCall} groups a record's observations, while a \term{VCFSample} identifies a source column; field definitions remain separate from their occurrence in a header.
PROV and DCAT support source descriptions, while SO and FALDO connect to alteration and location models without asserting normalized variant identity across files~\cite{prov2013,eilbeck2005so,bolleman2016faldo}.
VCF Core is a semantic vocabulary with classes, properties, declared domains and ranges, and a shallow subclass hierarchy; it carries no OWL restrictions, cardinality, disjointness, or inverse axioms.
Value and cardinality constraints are expressed as SHACL shapes~\cite{shacl2017}.
Terms and relationships can be browsed in the \href{https://ecrum19.github.io/vcf-core-vocabulary/}{VCF Core Vocabulary Explorer}\footnote{\url{https://ecrum19.github.io/vcf-core-vocabulary/}}~\cite{ocg2026}.

Two \emph{sample profiles} provide alternative representations.
The \textit{expanded} profile gives each sample's field value its own resource; the \textit{condensed} profile stores sample-ordered vectors whose individual values require decoding.
Both retain the same file, header, and record context, selecting version-specific registries and validation overlays from \term{fileFormat}~\cite{vcfc210}.
Our assessment distinguishes a documented representation, an example instantiating it, and an executed query agreeing with an expected answer.
Only the last establishes correctness within the tested scope; artifact inspection provides a separate basis for RQ4.

\subsection{RQ1: specification-derived assessment and curated inventory}
\label{sec:m-rq1}

We assess correspondence between VCF specificaiton and VCF Core in both directions: from specification requirements to their \textit{vcfcv} representation, and from the vocabulary to a curated inventory of source constructs.
These approaches have prescedent in previous ontology assessment studies~\cite{gomezperez2001evaluation,sabou2012ontologyevaluation}.
The first assessment starts from pinned, digest-verified VCF 4.1--4.5 specifications.
A \emph{requirement} expresses a specification rule extracted as a question with a checkable answer, following competency-question and requirements-specification established practices~\cite{gruninger1995methodology,suarezfigueroa2009orsd,lot2022}.
For example, R16 asks: ``Can \term{Number=A} values be associated with the correct ALT allele?''
Requirements retain links to their source passages.
We deemed binary encoding, compression, indexing, producer estimation algorithms, and general invalid-input rejection are outside the scope of this assessment.

\paragraph{Cases and expected answers.}
A \emph{case} pairs one requirement and VCF version with a \emph{fixture}: a small VCF file designed to expose the rule.
The fixture is materialized into a \emph{witness} graph and queried using SPARQL~\cite{sparql2013}.
Each case has an \emph{expected answer} authored from the specification and fixture before query execution, adapting SAMOD and executable ontology-testing approaches~\cite{samod2016,blomqvist2012ontologytesting,wisniewski2019competencyquestions}.
Queries were drafted with AI assistance and reviewed by a human.
Expected answers primarily draw on specification examples.
Answers are compared as multisets of string-valued rows, so missing, extra, or duplicated rows fail, and ordering is tested by projecting ordinals.
Thus, values such as \texttt{30} and \texttt{30.0} remain distinct.
The fixture's declared VCF version must match its case.

\paragraph{Retrieval, controls, and scoring.}
Each case runs in both sample profiles on two axes.
\emph{Preservation} permits decoding values from literals, whereas \emph{structure} requires graph relationships and prohibits the string-decomposition functions \term{REPLACE}, \term{SUBSTR}, \term{STRBEFORE}, and \term{STRAFTER}.
An empty-graph control rejects queries that return the expected answer without data.
A predicate-deletion control requires the answer to change after deleting at least one referenced property; it establishes dependence on some vocabulary data, rather than on every property mentioned.
Requirements are scored per applicable version, profile, and axis as demonstrated when all cases pass, partial when some pass, not demonstrated when all fail, and unassessed when no case exists.
Only demonstrated requirements enter the numerator; all applicable requirements, including unassessed ones, remain in the denominator with equal weight.

The VCF Core vocabulary repository's \href{https://github.com/ecrum19/vcf-core-vocabulary/blob/main/scripts/vcf_examples.py}{Python materializer}\footnote{\url{https://github.com/ecrum19/vcf-core-vocabulary/blob/main/scripts/vcf_examples.py}} builds witnesses from fixtures.
The materializer, vocabulary, and queries share authors, so a common misunderstanding remains possible despite separately authored answers and the inclusion of controls.
RQ2 therefore applies the same assessment to a separate set of witnesses generated an indepentent implementation to mitigate this potential flaw.
Separately, reserved INFO/FORMAT Number/Type declarations are extracted from the specification texts and compared with the corresponding version registries.
This tests explicit declarations, independently of prose interpretation.

\paragraph{Curated inventory.}
The second assessment links 104 VCF 4.5 logical constructs to vocabulary terms and supporting evidence.
Reviewers classify whether information is preserved, structurally retrievable, and enforced by a validation rule.
These evaluation approaches have also been used to assess semantic ontologies in past studies~\cite{gomezperez2001evaluation,sabou2012ontologyevaluation}.
Representation is full when both preservation and structure are supported, partial when only preservation is supported, and absent otherwise.
Enforcement is recorded separately and does not contribute to the representation score.
These curated judgments complement the executed VCF specificaiton requirement tests.

\subsection{RQ2: comparison with an independent RDF converter}
\label{sec:m-rq2}

We re-execute all RQ1 cases against witness graphs generated by VCF-RDFizer 3.0.3~\cite{vcfrConverter2026}, keeping fixtures, queries, and expected answers unchanged.
This converter executes RML mappings with RMLStreamer, whereas the \textit{vcfcv} materializer constructs triples via a Python script.
The programs share an author, so the comparison tests separate implementations without constituting replication by an unrelated group.
Every fixture is converted in both profiles, and both producers' graphs are generated during the run.
For each case, axis, and profile, we record whether both pass, either producer alone passes, or both fail.
We also compare the two profiles case by case.
Because producers mint different resource bases, fragment-bearing IRIs are compared by fragment alone; a wrong namespace with the correct fragment could therefore escape detection.

\paragraph{Semantic round-trip.}
A complementary check reconstructs the seven fixed columns, sample genotypes, header lines, INFO entries, and non-GT FORMAT values from structured RDF properties and compares them with the source.
Use of the preserved-source properties \term{infoRaw}, \term{sampleDataRaw}, and \term{genotypeString} are forbidden.
Deliberate alterations or deletions of genotype, field, and header data verify that mismatches are detected.
A leading phase indicator is normalized because VCF 4.4-5 permits equivalent forms such as \texttt{|0|1} and \texttt{0|1}; allele order, missing calls, ploidy, and intervening phase indicators must still match exactly.
The check uses only expanded graphs because condensed decoding requires an accessor the converter does not yet emit.
RQ1 and RQ2 use exact comparison, without sampling or tolerance thresholds.

\subsection{RQ3: integration under local alleles}
\label{sec:m-rq3}

RQ3 tests whether the representation supports a reproducible join to external statements while retaining source context.
A synthetic VCF contains four sites represented both locally and globally, with one sample, and is converted in the expanded profile.
Its graph is combined in memory with a separately authored local snapshot of five invented, flagged alterations.
The two inputs share no identifiers.
Listing~\ref{lst:localallele} joins them on contig, position, reference allele, and alternate allele, then retrieves supporting depth through \term{forAllele}.
This assumes the same reference assembly, unchecked against the VCF reference declaration, and identical as-written alleles without normalization or VRS identification.
The sample identifies a VCF column, not a patient.

\begin{lstlisting}[caption={The integration \emph{query}, abridged; \term{forAllele} resolves the \term{Number=LR} frame of reference.},label={lst:localallele}]
# 1. the flagged alteration, from the external annotation snapshot
?annotation a ex:FlaggedAlteration ; ex:contig ?contig ; ex:position ?position ;
            ex:referenceAllele ?ref ; ex:alternateAllele ?alt .
# 2. the same alteration as written in the VCF file
?record vcfc:chrom ?contig ; vcfc:pos ?position ; vcfc:ref ?ref ;
        vcfc:hasCall ?call ; vcfc:hasAltAllele ?altAllele .
?altAllele vcfc:alleleValue ?alt .
# 3. that sample's LAD value, and the declaration giving its cardinality
?call vcfc:hasSampleCall/vcfc:hasFormatValue ?field .
?field vcfc:declaredBy [ vcfc:fieldId "LAD" ; vcfc:fieldNumber ?number ] ;
       vcfc:hasValueItem ?item .
# 4. the depth for THIS allele, via the sample's own local allele set
?item vcfc:forAllele ?altAllele ; vcfc:itemValue ?depth .
\end{lstlisting}

The query selects flagged alterations with \texttt{LAD >= 20}, a threshold chosen to distinguish correct local-allele interpretation from positional misreading.
Please note, this example was chosen semi-arbitratily and does not exhibit clinical significance.
Expected rows are authored before execution and compared exactly across all eight projected fields, rather than by row count.
Each of the three excluded alterations is checked individually, and every returned row must cite the file actually converted, verified against the input path.
The example is restricted to the \texttt{Number=LR} field \texttt{LAD}; its annotations have no biological meaning and are held locally for deterministic execution.

\subsection{RQ4: comparison with existing models}
\label{sec:m-rq4}

One reviewer inspected published artifacts for GFVO, HERO-Genomics, GVO, and VCF2RDF against nine retrieval criteria (Table~\ref{tab:models})~\cite{baran2015gfvo,cazzaro2025hero,kawashima2023gvo,penha2017vcf2rdf}.
Verdicts are \textbf{E}, explicitly represented; \textbf{C}, representable with additional conventions; and \textbf{S}, outside stated scope.
The criteria concern VCF interpretation context, and S denotes a difference of purpose rather than a defect.
Artifact digests identify the inspected versions; VCF2RDF's terms were inspected, while converter behaviour was taken from its paper rather than execution.
GA4GH VRS is not scored because it addresses computable variation identity rather than source-file representation~\cite{wagner2021vrs}.
This assessment measures documented support, not the capabilities of extensions or applications built around these models.

\paragraph{Evaluated artifacts and reproduction.}
\label{sec:reproduction}
All results use released VCF Core 2.1.2~\cite{vcfc210} and VCF-RDFizer 3.0.3, with the latter's container pinned by digest.
The \href{https://github.com/ecrum19/SWAT4HCLS_2027}{experimental repository}\footnote{\url{https://github.com/ecrum19/SWAT4HCLS_2027}} provides requirements, fixtures, queries, expected answers, per-RQ procedures, run scripts, and pinned artifacts in \path{PINS.md}.
All references to "local" files or results can be found in the experimental repository listed above.
Runs record specification digests, commands, graphs, results, and environment information, including the dependency rdflib~7.6.0 for query execution.
