## Build

There is no repository-level Makefile: each manuscript directory builds on its own,
so the two can never collide in a shared build tree.

```sh
make -C short_paper            # short_paper/main_short.pdf
make -C short_paper pages      # last page of main matter, references excluded
make -C short_paper clean      # remove .build/, keep the PDF

make -C long_revised           # long_revised/main_long.pdf
make -C long_revised figures   # regenerate the RQ1 coverage figure
make -C long_revised pages
make -C long_revised clean
```

Building requires `latexmk`, `pdflatex` and BibTeX with the packages CEURART uses,
including the `elsarticle-num-names` style; the current PDFs were built with
TeX Live 2026.

Each directory carries its own `sources.bib`. `short_paper/` takes the document
class and logos from the shared [template/](template/) directory; `long_revised/`
keeps its own copies of those three files so that it builds from an extracted
archive with no other part of this repository present.

Diagrams are TikZ and code samples use `listings`, so for `short_paper/` the
sources plus a TeX installation are the whole build. `long_revised/` additionally
includes one generated figure, `figures/requirement-coverage.pdf`, produced by
[`scripts/requirement-coverage.py`](long_revised/scripts/requirement-coverage.py)
from `RQ1/results/summary.json`. That PDF is committed, so `matplotlib` is needed
only to regenerate it, and the script must be run from a full checkout because it
reads the RQ1 results from this repository root.

`long_revised/examples/` holds tab-delimited counterparts of the fixtures printed
in that manuscript, together with the full text of the queries its listings show or
describe; see [long_revised/examples/README.md](long_revised/examples/README.md).

## Evidence

One directory per research question. Each is self-contained and fetches what it
evaluates from GitHub at a pinned revision, so none needs a local checkout of the
vocabulary or the converter. Every directory has an `EXPERIMENT.md` explaining its
premise, procedure, results and known weaknesses; start there.

| | Question | Run |
| --- | --- | --- |
| [RQ1/](RQ1/) | Does VCF Core preserve and represent everything defined in the VCF specification (including file and header context, allele-dependent field values, sample genotypes and phasing, version-specific constructs, etc.)? | `sh RQ1/run.sh` |
| [RQ2/](RQ2/) | Do VCF graphs generated by two different conversion methods represent the VCF specification definitions from RQ1, and can a source VCF file be reconstructed from generated VCF graphs (i.e. round-tripping)? | `sh RQ2/run.sh` |
| [RQ3/](RQ3/) | Can VCF graphs enable the integration of VCF data with external data while retaining the initial VCF file, record, sample, and declaration context to answer a complex question? | `sh RQ3/run.sh` |
| [RQ4/](RQ4/) | How does VCF Core compare to other existing VCF semantic models at answering nine usage-oriented information-retrieval questions from VCF data? | `sh RQ4/fetch.sh` |

The questions above are quoted from the current manuscript, `long_revised/`.

RQ4 is a reading exercise rather than an executed test; its script only re-fetches the
inspected artifacts and records their digests.

[PINS.md](PINS.md) lists every pinned artifact, commit and image digest.
RQ2 writes a self-contained run directory holding the environment, every command with
its exit code and duration, the converted graphs and the results; the run the paper
cites is in [RQ2/runs/](RQ2/runs/).

[coverage/](coverage/README.md) holds the fixtures behind the short paper's worked
example.
